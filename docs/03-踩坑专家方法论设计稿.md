# 交付物 3：踩坑专家通用方法论设计稿 v1.0

> **定位一句话**：任务执行前的**风险测绘仪**——诚实地测绘坑位分布，绝不承诺「坑已踩完」（坑不可穷尽是公理，不是缺陷）。
> **设计依据**：交付物 2《方法论综述》的证据链 + 《坑点案例库 v1》的 10 条一手考题。每个机制标注来源（综述编号 / 案例编号），可追溯。
> **独立性声明**：本设计稿独立产出；《踩坑专家方法论全集 v0.2》（WorkBuddy 侧既有稿）仅作为对比对象进入附录 C，未作为设计输入。

## 〇、三条设计公理

1. **坑不可穷尽**：任何预检都是对已知坑的采样。unknown unknowns 只能靠「盲区声明」显式承认，不能靠沉默假装不存在。（综述 1.6/1.7：模型自知有限且不可靠）
2. **内省不算验证**：同一上下文里的「我再想想」不产生新信息。（综述 1.3 [A] 级证据：无外部反馈的自我纠错无效甚至有害）验证必须来自外部信号：工具、检索、实测、独立上下文。
3. **披露重于正确**：用户最大的损失不是「漏了坑」，而是**分不清哪些是验证过的、哪些是猜的**，只能靠事后质疑质检（案例 D7）。因此输出契约的完备性优先于坑清单的长度。

## 一、总体架构：五层流水线

```
任务输入
  │
  ▼
【L0 定级层】任务画像 + 风险定档 ──────── 决定跑多深（防流程过重，案例 D 类任务不过度、改错字不启动）
  │
  ▼
【L1 挖坑层】三路生成器并行 ──────────── 假设倾倒 / 预验尸回推 / 坑库相似召回
  │
  ▼
【L2 过滤层】真实性过滤与分级 ────────── 真坑🐯 / 中风险🟡 / 大象🐘 / 纸老虎🐺（防叙事性假风险，综述 2.2）
  │
  ▼
【L3 验证层】坑点→探测动作配对 ───────── 能实测的实测，能检索的检索，测不了的进未验证区（综述 3.1/3.2/3.5）
  │
  ▼
【L4 披露层】三态契约输出 ───────────── 已验证✅ / 未验证❓ / 盲区🚫，空区显式写空（案例 D7）
  │
  ▼
【L5 沉淀层】坑卡回写 ───────────────── 证实坑/漏报坑全部结构化入库，相似召回复利（综述 5.3/5.5）
```

## 二、十二个核心机制（M1–M12）

每个机制 = 一句话规则 + 来源映射 + 回放命中情况（详见附录 B）。

### M1 用户约束画像先行（案例 D2、D3 的直接解药）

**规则**：预检维度清单的第一来源是**用户真实约束**，第二来源才是通用清单。任何「够用/兼容/匹配」类判断前，必须先生成「用户约束画像」：读得到的用户环境数据（历史用量、上下文水位、既有配置、设备/网络约束）逐项列出；读不到的字段显式标注「画像缺失」，此时容量类结论强制降级。

- 实操：接入类任务 → 必检项 = 用户历史上下文水位、月耗、并发模式（可从账本/会话记录读取）；读不到就先问，问不到就降级。
- 来源：案例 D2（232K 坑：验证清单按通用模板而非用户 26–41 万上下文水位定制）、D3（两天样本）。
- 为什么有效：通用清单查「大家都怕的坑」，画像推导查「**这个用户会撞上的坑**」——232K 对一般用户不是坑，对该用户是致命坑。

### M2 量纲审计前置（案例 D4）

**规则**：任何比较/排序/推荐类结论，先完成「计量口径审计」：所有比较对象的计量基准（计价口径、汇率、单位、含税/手续费、有效期、版本）换算一致后才允许输出排序。审计过程附在报告里，可复核。

- 价格/额度类任务的必检字段表：计价基准（闲时/高峰/混合）、缓存计价、隐藏费用、过期规则、窗口规则、退款条件。
- 来源：案例 D4（高峰价 vs 闲时价，「两家的 $1 不是同一种美元」）。

### M3 信源分级绑定动作（案例 D5）

**规则**：每条外部信息入库时标注信源等级——`A 官方一手` / `B 权威二手` / `C 社媒传言`。**C 级信源只能触发「核实任务」，不得触发「分析任务」**：基于 C 级信息的分析在完成 A 级核验前不得出现在结论区，只能整体进未验证区。

- 标注可信度 ≠ 免责完成。分级必须绑定动作。
- 来源：案例 D5（抖音「三天脉冲」未核实即展开完整分析，后全部作废）。

### M4 负面定性高证据门槛 + 检索边界披露（案例 D1）

**规则**：
1. 指控类负面定性（山寨/造假/跑路/恶意）的证据门槛**高于**正面结论：必须至少两类独立渠道（搜索引擎 + GitHub/官网/社区任一）交叉命中，才允许写入结论区；
2. 「搜不到」类否定性证据必须附检索边界：渠道、关键词、日期，并显式声明「检索时滞——新事物可能未被收录」；
3. 负面定性必须附「证伪动作清单」（做什么能推翻这个定性），供用户低成本复核。

- 来源：案例 D1（「搜不到」当「不存在」，把 10 万星开源项目误判山寨）。

### M5 样本量强制声明（案例 D3）

**规则**：容量/速率/成本类结论必须显式声明输入数据的**样本量、覆盖期、遗漏场景**（如「样本=2 天账本，未覆盖赶工周」）。样本不足以支撑结论时，结论降级为「待验证假设」并列出补数据动作（读全量历史/问用户/实测一周）。**数据画像缺失本身就是一个必须上报的坑。**

### M6 异常信号触发器 + 条款层级枚举（案例 D6）

**规则**：
1. **too-good-to-be-true 自动升档**：异常便宜/异常顺利/异常优惠 → 自动升到深审档，触发反欺诈式三问——谁在补贴？为什么？代价藏在哪？
2. **条款层级枚举**：涉及套餐/合同/额度时，强制逐层填值——总额度 / 单项额度 / 促销加成 / 窗口限制 / 过期规则 / 隐藏费用，**缺层即坑**（读不到就标「该层不透明」）；
3. **优势归属检验**：每项候选优势必须回答「在用户的实际使用路径上是否成立」（如「CLI 专属红利」对走 API 的用户不存在）。

### M7 三态披露契约（案例 D7；综述 3.5 升级）

**规则**：报告中每一条陈述落入且仅落入一个态：

| 态 | 准入标准 | 必附 |
|---|---|---|
| ✅ 已验证 | 有外部信号支撑（实测/检索/工具输出） | 证据链：来源 + 验证方式 + 时间 |
| ❓ 未验证 | 有理由怀疑但未验证 | 原因 + 补验动作（5 分钟内可执行的） |
| 🚫 盲区 | 本任务类型中系统性看不见的坑类别 | 预注册声明（类比利益冲突披露） |

**空区显式写空**（「本区为空」并给依据），禁止省略。「验证通过」四个字禁止裸用——必须带验证维度清单（验了什么、没验什么）。

### M8 真实性过滤与分级（综述 2.2；Shreyas Doshi 框架）

**规则**：挖坑层原始产出全部过过滤层：每条「坑」回答「这是具体证据指向的真风险，还是放之四海皆准的叙事？」（判断标准：该条是否让用户停下来查证一个具体事实/重算一个具体数字）。过滤后分级：

- 🐯 真坑（阻断级）：动手前必须处理；
- 🟡 中风险：有对策即可推进；
- 🐘 大象：今天没事、条件触发即致命，进监控区（附触发信号）；
- 🐺 纸老虎：识别后**不设防**，显式列出以防后续重复挖出（防清单通胀）。

### M9 多层检查防重叠（综述 4.3 瑞士奶酪 [A]）

**规则**：深审档的检查至少分三层，**各层查不同维度**（层间洞不重叠）：任务语义层（需求歧义/目标漂移）、数据与口径层（样本/量纲/信源）、执行环境层（工具链/权限/缺省行为）。每层预设自己的失效模式（「如果这层漏了，下一层怎么兜」）。

### M10 缺省行为必测（案例 E1、E3）

**规则**：第三方组件/参数/服务的**缺省语义默认为「未知」**，禁止按常识推断（「不传参数=关闭」是案例 E1 的原坑）。信任等级固定为：`读源码 > 实测 > 官方文档 > 猜测`，报告标注每条依据的等级。两样都做不了 → 标 ❓ 并附「最小实验设计」。

### M11 配置即验证（案例 E2）

**规则**：产出任何配置文件/manifest 后，**必须真实加载解析一次**才允许标 ✅（YAML 的 `off`→`false`、JSON 的类型强转、环境变量字符串陷阱均在坑卡库）。写完不跑 = 未验证。

### M12 坑卡回写与相似召回（综述 5.1–5.6）

**规则**：
1. 每次踩坑结束（无论坑是否发生）产出回写条目，格式见第四节坑卡 schema；
2. **未遂优先**：被预检拦下的坑、低损害小坑优先记录（海因里希：未遂是大坑的先导）；
3. 下次任务进入 L1 时，按任务相似度召回历史坑卡（美团 COE 模式：细粒度、带业务语义的记录才有召回价值）；
4. **漏报与谎报分轨**：漏报（事后发现、但当时未验证区有如实披露）→ 可原谅，正常回写；谎报（声称已验证但无证据链）→ 流程缺陷，追根因修流程。复盘对事不对人（无责复盘原则）。

## 三、档位与触发

### 3.1 三档服务（定级层输出）

| 档位 | 耗时目标 | 运行的机制 | 适用 |
|---|---|---|---|
| **T0 快扫** | 分钟级 | M1 简版 + M5 + 坑库速查 + M7 三态输出（允许大量 ❓） | 低风险小任务、改错字级改动 |
| **T1 标准**（默认） | 十分钟级 | M1–M7 全部；🐯 真坑实测验证 | 常规需求 |
| **T2 深审** | 小时级 | 全部 + M8 FMEA 评分（S/O/D，隐蔽度 D 权重最高）+ M9 三层 + 对抗角色（红队多角度攻击） | 高风险决策：采购/迁移/发布/不可逆操作 |

**自动升档触发器**：①M6 异常信号；②任务涉及不可逆动作（付款/删除/发布/公开外发）；③用户明示高风险。**降档触发器**：用户明示低风险 + 任务无外发副作用。

### 3.2 触发时机（三种，按强制力递增）

1. **显式手动**：`/踩坑 <任务>`（斜杠命令）或对话中说「先踩坑」；
2. **建议性自动**：检测到计划类信号（plan 文件引用、重大决策句式、支付/发布意图）→ 主动建议预检（不阻塞，参考 parcadei 的 UserPromptSubmit hook 模式）；
3. **强制性门控**（仅插件形态可实现）：不可逆操作前置检查——未携带有效踩坑报告则拦截并要求补跑。**这是 Skill 与插件的能力分水岭**（详见交付物 4）。

### 3.3 输入格式

```
任务描述（必需）
+ 档位指定（可选，缺省 T1；可被 3.1 触发器改写并告知用户）
+ 画像数据源授权（可选：允许读本地账本/会话记录/配置——M1 的燃料；未授权则相关字段标「画像缺失」）
+ 关注点（可选：用户点名要查的维度）
```

## 四、分领域坑位框架

### 4.1 领域注册表

每个领域一个目录，含 `capability.md`（能力声明：**能防什么、不能防什么**——按格承诺不越格）+ `pitfalls/`（坑卡库）。

| 领域 ID | 名称 | 首版状态 | 能力声明（首版） |
|---|---|---|---|
| `research-decision` | 调研/采购/决策域 | ✅ 首批实装（坑卡 8 张，源自案例库 D1–D8） | 能防：事实性陷阱、口径坑、样本坑、信源坑、隐性条款坑。不能防：未来事件预测、对手策略 |
| `code-integration` | 代码/工程集成域 | ✅ 首批实装（坑卡：E1–E3 + 通用工程坑 + awesome-falsehood 机器化底料） | 能防：缺省行为坑、配置暗雷、权限/沙箱不一致、环境依赖、常见语言级 falsehoods。不能防：架构品味、业务逻辑正确性（需测试） |
| `math` / `science-ml` / `creative` | 数学 / 科学ML / 创意 | ⏳ 仅注册，能力声明为「未验证」 | 接口占位：坑卡 schema 复用，不发布任何承诺 |

> 领域扩展协议：新领域 = capability.md（先声明边界）+ ≥5 张经来源标注的坑卡 + 至少 1 条案例回放，三件套齐才注册。

### 4.2 坑卡 schema（YAML frontmatter + 正文四元组）

```yaml
id: RD-001                    # 领域前缀 + 序号
domain: research-decision
title: 把「搜不到」当「不存在」
hazard_type: 事实性陷阱        # 六类：常见错误/隐含前提/易错环节/工具链环境/事实性陷阱/逻辑漏洞
severity: 7                   # S：发生后的伤害 0-10
detectability: 9              # D：隐蔽度 0-10（灵魂指标：高D=毫无征兆的隐形坑）
trigger: 对新事物下负面定性时   # 什么场景该召回本卡
latent_condition: 检索时滞      # 长期隐患（无责复盘二分之「潜伏隐患」）
verified: case-replay         # case-replay（案例回放过）/ literature（文献支撑）/ unverified
source: cases/D1              # 溯源
```

```markdown
## 症状（❌ 错误形态）
[真实反例——黄金三元结构之一]
## 正确做法（✅）
[可执行的正确动作]
## 原因（why）
[为什么会踩：认知机制或系统机制]
```

首版两域坑卡清单（详见附 `/pitfalls/` 目录设计，实现阶段落地）：
- research-decision：RD-001 搜不到≠不存在｜RD-002 验证维度按通用清单而非用户约束｜RD-003 样本量欺诈｜RD-004 计量口径不一致｜RD-005 低可信源先分析后核实｜RD-006 纸面额度与总闸（条款层级）｜RD-007 优势归属错配｜RD-008 验证边界不透明（裸「验证通过」）
- code-integration：CI-001 缺省语义按常识推断｜CI-002 配置写完不加载｜CI-003 组件默认值不一致（never 档无 sandbox）｜CI-004 类型强转暗雷（YAML off/JSON）｜CI-005+ awesome-falsehood 机器化条目（时间/地理/姓名/i18n 等 falsehoods 精选）

## 五、结果校验方式（DoD 过程标准）

**一次踩坑「完成」，当且仅当六条全满足**（全部是过程指标，无一条要求「结果上没有坑」——保证结果完美只会催生谎报）：

1. **档位已声明**：本报告的档位与升/降档触发器记录在案，未越格承诺；
2. **画像已生成**：用户约束画像存在，或「画像缺失」及其影响已显式声明（M1）；
3. **覆盖率 100%**：所属领域坑卡库逐卡扫描（报告中附扫描计数），不许抽样跳过；
4. **🐯 验证率 100%**：所有阻断级坑三态完整——✅ 的有证据链，❓ 的有补验动作（M7）；
5. **披露率 100%**：三区全部显式输出（空区写空并给依据）；
6. **回写就绪**：本次坑卡回写条目已生成（M12）。

**判定规则**：六条全过 = 合格（哪怕事后发现漏了大坑，走漏报轨回写）；任何一条虚报 = 不合格（哪怕碰巧没出事，走谎报轨追流程根因）。

## 六、防「流程自身失效」设计（自我红队）

按综述 4.4（清单的失效面）与瑞士奶酪原则，预检流程自己也可能是坑源：

| 流程失效模式 | 防线 |
|---|---|
| tick-box 空转（勾了没做） | DoD 第 3/4 条要求附计数与证据链，非打勾 |
| 清单通胀（坑卡越加越多→没人看） | 坑卡宁缺毋滥、版本化演进（综述 5.8）；🐺 纸老虎显式归档不重复挖 |

| 踩坑者谄媚（顺着方案找补） | 挖坑提问与原方案文本隔离生成（综述 3.2 CoVe）；对抗角色独立上下文 |
| 因果过度推断（相邻事件写成因果） | 输出规范明令：坑卡 why 字段须区分「相关」与「因果」（综述 5.7） |
| 方法论自身翻车 | 方法论修订记录开放（继承「元坑登记簿」思想：自身每次失效回写） |

## 附录 C：与 v0.2 既有稿的显式对比（按用户决策输出）
