## 第 2 步：读 8 份事故（约 1 小时，每份 6–8 分钟）

从 danluu 的 256 份汇编里挑的，分三组，正好对应要做的三张卡。**每份只摘三样**，写在下面的模板里：**哪一步断了 / 什么迹象能提前看见 / 下车怎么验**。

### A 组 → 卡 A「半套生效」（变更只落到系统的一部分）

1. **GitHub DNS 事故** <https://github.blog/news-insights/the-library/dns-outage-post-mortem/>
   Puppet 改 IP 后只重启了权威 DNS、没重启缓存 DNS → 查询超时；抢修时重建 zone 文件的那个 API 自己又依赖 DNS → 生成了一份坏的 zone。
   教的道理：**一次变更落到了一半的组件上；而且恢复路径依赖着正在坏的东西。**
2. **CircleCI 2025-04-04 工作流延迟** <https://discuss.circleci.com/t/post-incident-report-april-4-2025-delays-in-starting-workflows/53113>
   数据库蓝绿升级「机械上成功了」，但切换后的库统计表没更新，每条查询都在读盘；ANALYZE 跑早了，同一次部署里的第二次大版本升级把它抹掉了。
   教的道理：**「步骤都执行了」≠「步骤的效果都在」。**
3. **GitLab 2017-01-31 删库** <https://about.gitlab.com/2017/02/10/postmortem-of-database-outage-of-january-31/>
   请求洪峰 → 复制延迟 → 疲劳的管理员删错目录 → 丢 6 小时数据；五种备份全部没起作用。
   教的道理：这张主要归 CODE-026（已有），但「复制做到一半、人上去手动补」是半套生效的前传——当 A 卡的第三份证据。

### B 组 → 卡 B「重试放大」（小故障被重试打成大故障）

4. **GitHub 2025 年 5 月 10 日** <https://github.blog/news-insights/company-news/addressing-githubs-recent-availability-issues/>
   一个低效的 API 端点 + 调用方「超时就重试」→ 负载放大 7 倍。（同一篇里 5 月 9 日那段是「回滚自己失败」，归 A 组补充。）
   教的道理：**重试是放大器，不是修复器。**
5. **Cloudflare 2025-09-12 控制台/API 宕机** <https://blog.cloudflare.com/deep-dive-into-cloudflares-sept-12-dashboard-and-api-outage/>
   前端一个 React 依赖数组配错 → 对后端疯狂重复调用 → 压垮 Tenant Service → 级联到全部 API。
   教的道理：**放大器可以藏在客户端里，服务端看到的只是「突然爆了」。**
6. **Google Cloud 存储级联** <https://status.cloud.google.com/incident/storage/19002>
   一次为了应对流量上涨的配置改动，把 blob 查找系统的一部分压过载 → 级联到 Gmail/Photos/Drive。
   教的道理：**「为了扛住」做的改动本身成了压垮的那根稻草。**

### C 组 → 卡 C「没设超时 = 无限等」（很可能是 CI-001 的子卡）

7. **incident.io 两周间歇超时** <https://incident.io/blog/database-performance>
   请求等数据库连接池等到 20 秒；不是某一条慢查询，是争用散在很多端点上；修了 24 次部署才找到。
   教的道理：**池耗尽的症状是「随机慢」，不是「某处慢」，排查方向天然错。**
8. **incident.io PGAudit 锁死** <https://status.incident.io/incidents/01JRDFKAGE07YYDY0KZR137BX3/write-up>
   升级 Postgres 17 后重新启用 PGAudit；一次建空表的普通迁移触发扩展挂死、**持有关键锁、忽略超时信号**。
   教的道理：**「有超时设置」≠「对方会理你的超时」。**

### ⚠️ 第四类「重复提交/幂等」——这批汇编里一条都没有
