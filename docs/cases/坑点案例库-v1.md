## 回放验收协议

对每条案例问同一个问题：**如果当时「踩坑专家」按设计稿的完整流程跑一遍，这个坑能否在用户决策/动手之前被挖出来？**

| 判定 | 含义 |
|---|---|
| ✅ 能防 | 流程中存在明确机制，会确定性地命中该坑 |
| ⚠️ 部分能防 | 机制存在，但命中依赖附加条件（如用户提供某输入、某工具可用） |
| ❌ 不能防 | 超出现有机制覆盖，必须写入盲区声明 |

设计稿验收门槛：✅ + ⚠️ ≥ 80%。

## 一、调研/采购决策域（翻车主战场）

### 案例 D1：把「搜不到」当「不存在」——新产品误判山寨

- **场景**：对比三个 AI 编程平台。OpenDesign 名字、logo 与 OpenCode 高度相似，且搜索引擎搜不到其独立资料。
- **当时判断**：「山寨/跑路的嫌疑不小」，建议「核实前先别碰」。
- **坑的真相**：正经开源项目（github.com/nexu-io/open-design），开源不到半年 10 万 Star，其基准测评被国内媒体引用。用户一句「不信你去网上查查」后，换关键词一查即现形。
- **为什么当时没发现**（根因）：
  1. 检索时滞盲区：新产品搜索引擎尚未收录，把「搜索引擎搜不到」当成「不存在」的证据；
  2. 弱证据强结论：「名字像」被当成碰瓷信号，直接跳到「山寨嫌疑」的负面定性；
  3. 单渠道检索：只搜了搜索引擎，没查 GitHub 本身、没换关键词。
- **应然的发现方式**（机制需求）：
  - 负面定性结论（指控类：山寨/造假/跑路）必须满足比正面结论更高的证据等级，且必须列出「证伪该定性所需的检索动作」；
  - 「搜不到」类否定性证据必须显式标注检索渠道、关键词、时间，并声明「检索时滞」边界；
  - 影响决策的重大定性必须多渠道交叉（搜索引擎 / GitHub / 官网 / 社区贴吧）。
- **回放考题**：面对一个「搜索引擎查无资料」的新产品，踩坑专家的输出应长什么样？

### 案例 D2：232K 上下文硬顶漏查——验证维度按通用清单而非用户真实约束

- **场景**：推荐将 OpenDesign 渠道接入用户主力工作流。事前验证了价格、双协议、缓存透传、工具调用、流式输出、长生成——六项全绿，「技术层干净」。
- **当时判断**：「全链路验证通过」，可接入。
- **坑的真相**：该网关 `/models` 元数据里明写 `context_budget: 232000`——单请求上下文硬顶。用户主力会话上下文 26–41 万 token，**75.4% 的 token 消耗发生在超限会话里**。用户接入后怒斥「这个有坑你不早说」。
- **为什么当时没发现**（根因）：
  1. 验证清单是「通用渠道接入清单」（价格/协议/缓存/工具），而不是从**用户真实使用画像**（历史会话上下文水位 26–41 万）推导的定制清单；
  2. 元数据做了部分字段读取（模态、成本档、上下文标称值），但没做**全字段扫描**——`context_budget` 就躺在读过的那个接口返回里；
  3. 「已验证」声明不含验证维度的完整性边界，六项全绿制造了虚假安全感。
- **应然的发现方式**（机制需求）：
  - 预检维度必须首先从用户真实约束推导（本例：读历史会话的上下文水位 → 「单请求上下文上限」成为必检项），通用清单只做兜底；
  - 接口/文档/条款的元数据要全字段枚举，未知语义字段（如 budget vs limit）必须标记并查明，而不是只读自己认识的字段；
  - 验证报告必须披露「验了哪些维度、没验哪些维度」，禁止用「验证通过」暗示全面覆盖。
- **回放考题**：用户说「帮我接入一个 API 渠道」，踩坑专家的必检维度清单从哪里来？

### 案例 D3：两天样本推「够用」——容量结论的样本量欺诈

- **场景**：估算用户月消耗，依据是本地账本 10/11–10/12 两天的均值（≈$29/月）。
- **当时判断**：「三家额度全都覆盖」「$60 对你依然够用」。
- **坑的真相**：用户真实日耗 5–10 亿 token，估算偏差 3–7 倍；照原结论选的套餐上限仅够真实用量的零头。用户自报量级后结论整体推翻。
- **为什么当时没发现**（根因）：
  1. 关键容量结论建立在极小样本上，且**样本量从未向用户声明**；
  2. 用均值代替分布：两天恰好是低强度日，重度日（赶工、批量任务）完全没进样本；
  3. 没有主动询问或全量读取用户的真实用量模式。
- **应然的发现方式**（机制需求）：
  - 任何「够用/不够用」类容量结论，输入数据的样本量、覆盖期、遗漏场景必须显式声明；
  - 样本覆盖不足时，容量结论必须降级为「待验证假设」并列出补数据动作，而不是直接给结论；
  - 用户画像数据（历史用量）缺失本身就是一个必须上报的坑。
- **回放考题**：基于有限样本下容量结论前，踩坑专家必须强制完成哪三个动作？

### 案例 D4：两家的「$1」不是同一种美元——比较类结论的口径陷阱

- **场景**：对比 OpenDesign（月额度 $120）与 Command Code（月额度 $60/80/100）谁的额度多。
- **当时判断**：「纯比每 $10 买多少额度：OpenDesign $120 > OpenCode $80 > Command Code $60，OpenDesign 额度多所以赢。」
- **坑的真相**：OpenDesign 按**高峰牌价**扣额度（输入 $0.3/M），Command Code 按**闲时牌价**记账（输入 $0.15/M）——同样 1 美元额度，后者能买 2 倍 token。统一口径后 Command Code 的 $100 ≈ OpenDesign $200 的实际量，排序反转。该坑由用户看到官方计价表后才暴露。
- **为什么当时没发现**（根因）：
  1. 只比了面值（美元数字），没比含金量（每美元买多少真实资源）；
  2. 「计量口径一致」是比较类结论的隐藏前提，从未被显式检验；
  3. 计价基准藏在各家文档不同位置，通用对比模板里没有「扣费口径」这个字段。
- **应然的发现方式**（机制需求）：
  - 比较类结论必须先完成「量纲审计」：把所有比较对象换算到同一计量口径后才允许排序；
  - 价格/额度类调研的必检字段含：计价基准、峰谷规则、缓存计价、过期规则、隐藏费用；
  - 排序结论必须附口径换算过程，可复核。
- **回放考题**：三家平台额度对比，踩坑专家的第一步是什么？

### 案例 D5：抖音信源未核实先分析——低可信源上搭建分析大厦

- **场景**：用户带来一条抖音视频：「Command Code 限时三天 100 美金额度」。
- **当时判断**：基于「三天脉冲」口径做了完整分析（含风控动机、用户收益测算），结论「对你鸡肋」。虽在事实梳理环节标注了「⚠️ 仅抖音来源，无法证实」，但分析照样展开了。
- **坑的真相**：官方页面显示实为**月度额度从 $80 提升到 $100**（至 10/16 截止），不是三日脉冲。整层分析作废，用户被误导一轮。
- **为什么当时没发现**（根因）：
  1. 信源分级只做了「标注」，没有配套**强制动作**——低可信源只应触发「核实任务」，不应触发「分析任务」；
  2. 在未核实的事实上搭建了完整推理，标注⚠️被当成了免责而非行动指令；
  3. 官方一手源（pricing 页/公告）的核验被跳过——成本很低但没做。
- **应然的发现方式**（机制需求）：
  - 信源分级必须与动作绑定：低可信源信息进入分析前，必须先完成一手源核验；核验不了则整条信息只能进「未验证区」，不得参与结论推导；
  - 「可信度标注」与「是否允许基于其推理」是两件事，流程上要分开。
- **回放考题**：用户带着一条短视频消息来咨询，踩坑专家的流程第一步是什么？

### 案例 D6：「便宜得离谱」没有触发深挖——异常信号与条款层级漏读

- **场景**：用户问「为什么会比官方便宜这么多，会不会有什么缺点」，后又追问「你肯定是漏算了什么坑」。
- **当时判断**（第一轮）：给出「批发价 + 烧钱获客 + 削峰填谷」三个机制解释，分析到此为止，结论「便宜是真的、不笨也是真的」。
- **坑的真相**（用户直觉反推后才挖出）：
  1. **纸面数字坑**：官方页同时写着「月度总额度 $70（全模型合计）」和「DS V4.1 Flash 月额度 $100（促销）」——总闸不放宽时 $100 是纸面数；
  2. **优势归属坑**：宣传的「Read 工具每月省 250 亿垃圾 token、98% 缓存命中」是它**自家 CLI** 的红利，用户走 API 接入完全享受不到，却被计入了对比优势。
- **为什么当时没发现**（根因）：
  1. 「好得不合常理」（$10 卖 $120 等值）本是标准的深挖触发器，但没有内建该触发规则，只在用户反问后才启动；
  2. 条款呈多层结构（总闸 / 单模型 / 促销 / 过期），阅读时没有「层级完整性」检查，只读到单模型层；
  3. 优势没有过「使用路径归属」检验：该优势在用户的实际使用方式（API 外接）下是否成立。
- **应然的发现方式**（机制需求）：
  - 「异常有利/异常便宜/异常顺利」自动升级为深审档，触发反欺诈式检查（谁在补贴、补贴的可持续性、代价藏在哪里）；
  - 条款/定价阅读强制做层级枚举（总额度/单项额度/促销/窗口/过期/费用），逐层填值，缺层即坑；
  - 每项候选优势必须回答「在用户的使用路径上是否成立」。
- **回放考题**：「便宜得离谱」应该在什么机制下自动触发升级审查？

### 案例 D7：错误总在用户质疑后才修正——披露缺失导致信任损耗

- **场景**：贯穿全程。上述 D1–D6 中六次判断失误，几乎全部由用户质疑（「不信你去查查」「啊，这个有坑你不早说」「你肯定是漏算了什么坑」）触发修正。用户原话：「这会严重影响我以后的判断和操作。」
- **坑的真相**：单次调研的失败不止是结论错，更是**验证边界不透明**——用户无法区分「AI 验证过的」与「AI 猜的」，只能靠事后质疑来质检，心智成本极高。
- **为什么当时没发现**：输出格式里没有强制的验证披露（验了什么/怎么验的/没验什么），结论无论深浅都呈现同等的自信外观。
- **应然的发现方式**（机制需求）：
  - 每条关键结论强制附证据链（来源/验证方式/验证时间），未验证的显式进未验证区；
  - 用户质疑应当被结构化接住（质疑 → 复盘 → 回写坑库），而不是临场认错完事。
- **回放考题**：一份踩坑报告要具备什么结构，用户才不需要靠质疑来质检？

### 案例 D8（正面）：WorkBuddy 做对的四件事——设计必须吸收

| 正面实践 | 对话中的实例 | 机制化方向 |
|---|---|---|
| 信源可信度分级 | ✅官方文档+多方交叉 / ⚠️仅抖音来源 | 分级必须绑定动作（见 D5） |
| 实测验证 | 拿 Key 真调端点，五项技术测试全跑 | 可实测项禁止纸面推断，动手测 |

## 二、工程/代码集成域（同一对话中的集成实操段）

### 案例 E1：「不传参数」≠「默认关闭」——网关默认思考开着

- **场景**：接入后想省钱关掉思考模式。界面无开关，实测发现：不传 `reasoning_effort` 时该网关**默认开思考**（回复「收到」两个字也烧 14 个 reasoning tokens），`default` 档是五档里实际最贵的档。
- **根因**：按常识推断「省略参数=关闭」；默认行为的语义因服务商而异，必须实测确认。
- **应然机制**：涉及成本/行为的参数，其「缺省语义」是必测项；不可测时标注「缺省行为未知」。
- **回放考题**：为用户配置批量任务参数时，哪个隐藏假设必须先验证？

### 案例 E2：YAML 的 `off` 键被解析成布尔 false

- **场景**：给思考档位配 `off/low/high/max` 四个键。YAML 1.1 规范里 `off` 是布尔假值，整个配置文件静默加载失败。
- **根因**：配置格式的类型强转暗雷；「加了引号锁死字符串」才是解。
- **应然机制**：配置类坑位库收录「YAML/JSON 类型强转」「环境变量字符串陷阱」等格式暗雷条目；配置改完必须真加载验证。
- **回放考题**：写完配置文件后的必做动作是什么？

### 案例 E3：插件默认档恰好不带 sandbox 字段——委派写文件只读失败

- **场景**：dsh 的 subagent-codex 插件三个权限档中，默认档 `never` 恰好是唯一不带 `sandbox` 字段的，导致 Codex 子代理落到自身默认只读沙箱，写文件报「只读权限」。
- **根因**：对插件行为的推断基于 CLI 测试经验，而 app-server 线程路径默认值不同；文档不写默认值细节，源码里才看得见（`lib/index.js:19-30`）。
- **应然机制**：第三方组件的默认行为必须「读源码或实测」，两样都做不了才允许按文档推断并标注；「默认值不一致」是集成类任务的高频坑，进坑位库。
- **回放考题**：集成一个新组件时，对其默认行为的信任等级怎么定？
