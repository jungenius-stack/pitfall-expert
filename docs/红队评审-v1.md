## ① 失效场景清单

### A. L0 定级（进 T0/T1/T2）

**A1. 循环依赖：在信息最少的时刻做资源最大的决策**

- 失效场景：用户说「帮我改一下这个测试库清理脚本，把保留期从 30 天改成 7 天」。任务文本全是低风险词汇（测试、清理、旧数据），模型定 T0——轻量子集，假设倾倒只有简版。但脚本的连接串指向生产库（用户口中「测试」是误称或配置漂移），「这真是测试环境」恰恰是假设倾倒完整版里最该攻击的隐含假设。定级准确性取决于对任务影响面的了解，影响面要挖了坑才知道，挖坑投入却由档位决定——三者在结构上互相等对方先出牌。T0 的轻量化（元坑⑫的修正方向）恰好把攻击力最弱的模式分配给了信息最少、定级最可能错的场合。
- 防线为何挡不住：升档触发器②「不可逆动作」自身就是一个纯模型判断——「清理 30 天前的旧数据」在文本层面很容易不构成「删除」。用一个无兜底判断去修补另一个无兜底判断。hooks 只拦命令字符串命中黑名单，不校验「定级与命令实际危险性是否一致」；命令不进黑名单时，T0 定级和破坏性结果之间没有任何闸门。
- 修复判据：构造一批「表面词汇低风险、实际后果不可逆」的任务（改配置指向生产、测试脚本连生产、清理共享目录），盲测定级分布。T0 误判率不为零即证明快速通行证发给了最危险的任务。

**A2. 定级是执行模型给自己定价工作量，存在系统性降档激励**

- 失效场景：「帮我看看这个免费 API 值不值得接」。M6 规定 too-good-to-be-true 自动升深审，但「异常」的判断权在模型——「免费增值很常见」→不异常→T1。跑 T2 意味着 FMEA+三层检查+红队对抗，摩擦全部落在本次上下文里，而漏坑的代价落在未来别处。定级、执行、自评 DoD 是同一个模型同一份上下文，利益三合一。
- 防线为何挡不住：DoD 第 1 条只查「档位已声明（含升降档触发记录）」——声明协商发生过不等于协商发生过，机检大概率只能查关键词存在。没有任何机制比对「任务实际触发的升档条件」与「记录的定档理由」。
- 修复判据：同一批高风险任务在「上下文余量充足」与「上下文接近耗尽」两种状态下分别定级，若降档率随上下文压力显著上升，即证明定级被摩擦预算而非风险驱动。

**A3. 「与用户协商」在主路径上是幽灵机制**

- 失效场景：主路径是 description 自动激活，agent 嵌在长任务流里执行技能，中间没有人类等待回复。协商的最可能形态是模型自问自答（「判断为 T1，继续」），报告里落一行「已协商」。元坑⑦修的是「术语看不懂」，没修「信息不对称」：用户如果比模型更懂风险就不需要这个技能；用户如果不懂，白话三选项他照样凭直觉点「小事，快扫」——给最不懂的人配了最重的决策权。
- 防线为何挡不住：硬门控只存在于 hooks 用户的 shell 层且只管命令；对没装 hooks 的用户（技能自己承认主路径是自动激活），协商环节零程序存在。
- 修复判据：审计自动激活场景下的报告，「协商」节是否存在真实用户回合；若 90%+ 为模型单方声明，该机制等于不存在，应删而非修。

### B. L2 真伪四分

**B1. 过滤标准测「具体性」不测「真伪」——而模型幻觉天然具体**

- 失效场景：L2 第一问的标准是「该条是否让用户停下来查证一个具体事实/重算一个具体数字」。具体≠真。模型扫「接入 AWS SDK for Rust」时输出「该 SDK 的 S3 client 在嵌套 tokio runtime 下有已知 hang 问题（GitHub issue #4xxx）」——版本、平台、症状俱全，置信度高，按标准轻松通过过滤并标 🐯。但这条可能是张冠李戴（记成了 Go SDK 的 issue）。用户去查证，搜不到——M4 的时滞声明「搜不到≠不存在」此刻反向生效：幻觉查不到反而显得更像真的，升深审，预算烧在编造的坑上，真坑被挤占。L2 的威胁模型错位：它挡住的是「不具体的废话」，放进来的可以是「很具体的胡话」，且越具体越容易升 🐯——幻觉倾向与真坑评级正相关。
- 防线为何挡不住：这条防护本身（M4）在幻觉场景下变成增强剂。硬约束 3 管 C 级信源，但模型脑内生成的「具体事实」不经过任何信源分级——它没有来源，或来源是「我的参数」。
- 修复判据：抽 ✅/🐯 区条目做人工溯源，统计「具体到版本号/issue 号但查无实据」的比例。不为零即证明过滤器放行方向反了。

**B2. 🐘 大象区是无人值守的监控区——「设了假防的真风险」**

- 失效场景：扫「数据库迁移到新实例」，发现「旧库触发器不被 pg_dump 默认导出」。这是 🐯（迁移完成即数据不一致）还是 🐘（迁移后第一周没人写那张表，看起来今天没事）？边界取决于模型对任务时间范围的理解，而 🐘 的处置是「进监控区并附触发信号」——报告交付后技能退场，**没有任何进程、钩子或后续会话负责执行这个监控**。🐘 实际是精致的风险陈列柜：把致命风险包装成「已知且已管理」，心理上完成处置，行动上零处置。三周后触发器逻辑静默丢失爆发。
- 防线为何挡不住：三态契约只管陈述真伪不管分级处置；DoD 六条无一条检查「监控区有没有人监控」；hooks 拦的是命令不是时间。
- 修复判据：明确定义监控信号的观测者和观测时机。答不出「谁在何时看这个信号」，🐘 档就是结构性虚假承诺，应强制并入 🐯 或 ❓。

**B3. 🐺 纸老虎=带免疫标记的合法丢弃通道；🟡=「裸对策」的法外之地**

- 失效场景（狼）：扫「用 Python 3.12 部署老 Django」，模型「知道」某弃用警告只是噪音→纸老虎。实际 3.12 移除了 distutils，装不上。纸老虎的判定依据只能是内省——公理 2 说内省不算验证，这个判断点恰好在公理的豁免位。更糟的是「防后续重复挖出」：L1 预验尸若再次推出该风险，会因已列纸老虎而跳过。单点误判被流程放大成全链路免疫，且丢弃方向与确认偏误同向。
- 失效场景（黄）：🟡 的定义是「有对策即可推进」，但对策的存在性、可执行性、由谁执行，格式上无任何强制——不需要证据链（那是 ✅ 的义务）也不需要补验动作（那是 ❓ 的义务）。🟡 是整份报告里唯一能合法携带「未验证的安慰」的区域，用户读完的感觉是「风险已识别且可管理」，这正是虚假安全感的最优藏身处。M7 禁裸「验证通过」，没有机制禁「裸对策」。
- 防线为何挡不住：硬约束 6 只管 🐯→验证器；四分里 🐺 和 🟡 是零约束条款。机检查不出「对策」二字背后有没有东西。
- 修复判据：取历史翻车案例盲跑，统计真坑最终落点分布（🐺/🐘/🟡 各占多少）；同时审计 🟡 区对策的事后执行率。落点分布本身就是判据。

### C. L4 三态归属

**C1. 证据链的「格式合规」≠「结论正确」，而 ✅ 区自带免疫效应**

- 失效场景：扫「接入某 SDK」，官方文档写「client 线程安全」，模型标 ✅（来源：官方文档/方式：检索/时间：今天），链三件套齐全、完全合规。实际该 SDK 三个月前的小版本引入回归，文档未更新——注意这不是元坑⑧（链接死了），链接活着、内容过时。用户按 ✅ 上多线程方案，线上数据竞争。关键损害在第二层：✅ 区向用户发射「这一块不用再想」的信号，误标条目被排除出复查范围（和纸老虎同构的免疫效应）。谎报轨的定义是「声称已验证但**无证据链**」不可原谅——追责边界画在了容易审计的地方（链在不在），恰好放过损害实际发生的地方（链对不对）。
- 防线为何挡不住：DoD 机检查的是验证器绑定和三区存在，不查证据→结论的推理有效性。「来源+方式+时间」三件套与结论正确性是正交维度，技能只审计前者。
- 修复判据：抽 ✅ 区做人工二判「该证据是否真能支撑该结论」。错误率非零则 ✅ 的语义应改为「已查证到 X（原文引用）」而非「已验证」——把模型的一次推理包装成事实状态，正是这个标签最危险的用法。

**C2. ❓ 区收纳了全报告最危险的条目，却占据注意力最弱的位置**

- 失效场景：L3 规定「绑不上可执行验证器的 🐯 一律降级 ❓」——即最危险的东西（被判为真坑但不可机器验证）被结构性转移进 ❓ 区。而 ❓ 的合规义务只是附一个「5 分钟内可执行的补验动作」，执行者是谁？报告交付后技能退场，补验作业发给用户，用户刚从 🟡 区读到「有对策即可推进」，❓ 区心理权重极低，跳过补验直接动手。三区的呈现顺序（✅→❓→🚫）注意力递减，信息确定性也递减——最不确定的信息获得最少的呈现强化，这个排布和风险分布是对着干的。
- 防线为何挡不住：无回访机制，补验执行率无人知晓也无人验收；机检只查 ❓ 区「有没有补验动作字样」。
- 修复判据：跟踪一批报告的补验动作实际执行率；低于某阈值（如 30%）即证明「补验动作」是免责话术而非流程，应改为「阻断待办：动手前必须完成以下检查」并置于报告头部。

**C3. 🚫 强制出现+空区给依据=制造完备性错觉，机检是其放大器**

- 失效场景：硬约束 7 和 DoD 5 要求盲区区必须存在且声明固定两项（未建卡领域+未覆盖范围）。于是每份报告尾部躺着一段模板化小字。真正致命的盲区（模型意识不到自己意识不到的东西）本来就不可能被写出——能被稳定写出的都是法定装饰。机检对三区查的是字符串存在性，全绿通过进一步向用户背书「这份报告是完备的」。防线在这里反向运作：它认证了它无法认证的东西。
- 防线为何挡不住：这条防线（机检）本身就是错觉源。
- 修复判据：删除强制出现要求，改为「有真实盲区才写」。若删除后报告质量不降（人工盲测），证明原来的强制是纯摩擦。

### D. L3 验证器铸造

**D1. 验证器输出的语义歧义+铸造者确认偏误**

- 失效场景：坑是「此配置项在新版本被改名」，模型铸造 `grep -r "old_name" src/`，命中 3 处。这证明什么？可能是坑存在（代码还在用旧名，升级即炸），也可能相反（命中说明有兼容层）。同一输出支持两个相反结论，而模型铸造时心里已有预期答案（它判了 🐯），执行结果会朝「证实」方向解读，然后标 ✅。注意这与元坑⑤不同：⑤是验证器太弱测不出问题，这里是验证器输出本身多义、解读权仍在模型手里——「可观测信号」铸造出来了，观测后的判断又退回了内省，公理 2 从后门回来了。
- 防线为何挡不住：M13 只约束「输出必须是可观测信号」，不约束「输出到结论的映射唯一性」。没有任何机制要求预先声明「输出 X ⇒ 坑成立，输出 Y ⇒ 坑不成立」。
- 修复判据：验证器必须先写判定表（哪种输出判哪态）再执行。审计已交付报告的验证器，无判定表的比例即歧义暴露率。

**D2. 验证器的环境假设零校验，且自身可成为新风险源**

- 失效场景：坑「磁盘可能不够迁移」，铸造 `du -sh /var/lib/postgresql`——用户是 Docker 部署，路径不存在，命令失败。按「必须实测」，失败被解读成「目录不存在=没装=无此坑」（错误推理）或勉强进 ❓。另一类更危险：验证「备份可恢复性」时模型给出 `pg_restore` 命令挨着生产实例跑——防坑技能在执行层引入新坑向量。还有自伤式死锁：模型铸造的验证器命中自家 hook 黑名单（测试删除行为时用 `rm`），hook 拦掉验证器，模型被迫改用更弱的检查或降 ❓，门控和验证层互相消耗。
- 防线为何挡不住：M13 无「无副作用」约束、无「环境存在性」预检；hooks 无法区分任务命令与验证器命令。
- 修复判据：验证器铸造规范中加入副作用分类（只读/写/不可逆），不可逆类默认禁止；统计验证器在真实异构环境的可执行率。

**D3. 铸造与执行分离，但结果不回填——验证器对坑分级不存在反馈回路**

- 失效场景：L3 自己写明「引擎只铸造验证器，执行由调用方完成」。于是「每条 🐯 必须绑定可执行验证器」的合规方式就是报告里**出现**一条命令。命令跑了没有？结果显示「没事」，这条 🐯 撤销还是保留？规范没说。验证器闭环缺最后一环：验证结果对坑分级的反馈不存在。整层 L3 的实际功能是报告装饰加责任转移，「必须实测」的义务通过「铸造一条命令」的文字游戏完成了形式履行。
- 防线为何挡不住：DoD 第 4 条查「验证器可执行」，不查「已执行、结果已回填」。机检同理。
- 修复判据：报告格式中验证器后强制跟「执行结果」字段（含「未执行+原因」）。空缺率即闭环缺失率。

**D4. 静态验证器对动态坑结构性失明，且该上限未入盲区声明**

- 失效场景：大量真坑的触发条件只在任务执行动态过程中成立（并发、负载、特定输入序列），任务前的静态检查（grep/查版本/读文档）对它们天然无效，而「绑不上验证器降 ❓」规则让动态坑系统性流进 ❓ 区——与 C2 合流：不可静态验证的风险自动降级为低注意力条目。技能的 🚫 区模板（未建卡领域+未覆盖范围）不含「动态触发类坑无法在事前验证」这类系统性上限声明。
- 防线为何挡不住：盲区声明模板枚举的两项与此无关；没有任何 DoD 条目要求披露验证器的覆盖类型边界。
- 修复判据：盲区模板中加入「本报告验证器类型覆盖：静态/动态」声明；动态覆盖为 0 的任务（迁移、压测、并发改造）必须显式声明「事前验证对本任务类失效」。

## ② 三个结构性弱点（按致命度排序）

**弱点一：防线密度与风险密度全面倒挂——确定性防线全部建在确定性环节，四个真正的不确定点零防线。**

这个技能有三道确定性防线：引擎（卡匹配）、hooks（命令黑名单）、dod_check.py（报告格式）。它们审计的全是格式与流程：字符串命中、关键词存在、三区齐不齐。而全部真实风险所在的四个判断——定级、四分、三态归属、验证器铸造——没有任何一道防线触及，全靠执行模型临场发挥，且四者的错误会互相背书（定错档→验证更弱→四分更随意→✅ 更不可信）。元坑⑬只承认了 T0 DoD 自检这一个小角，给出的兜底（机检）依然只查格式——一份由全错判断构成但格式合规的报告能全绿通过全部机检。B1、C1、D1、D2 都是它的直接下游：判断无校准，幻觉、过时知识、确认偏误在四个点上自由通过。

**弱点二：交付即退场，所有时间性承诺在交付瞬间变成坏账。**

技能的核心卖点是「verified，不是 claimed」，但它的验证故事有一半挂在报告之后的未来：🐘 的监控信号、❓ 的补验动作、验证器的执行、L5 回写的用户确认——全部预设「之后还有人接手」，而结构上没有第二次接触。技能实际上卖的是一次性风险感知，合同上写的却是风险管理。B2、C2、D3 是它的下游：🐘 监控区无人值守、补验无人验收、验证器执行不闭环，三者共享同一个根因——它们的价值全部依赖一个不存在的回访机制。

**弱点三：单次分类即终审，无重分类通道，错误朝「低估风险」方向单调累积。**

定级决定全部后续投入且中途无复核；🐺 纸老虎「防重复挖出」把丢弃变成免疫；✅ 区把通过变成免检；验证器输出的歧义解读偏向铸造时的预期。每个判断点的单次错误都被流程结构锁死，且所有锁死方向一致：朝风险被低估的方向。与降档激励（A2）叠加后，误差不是随机分布而是系统性偏移。A1、A3、B3、C1 是它的下游。
