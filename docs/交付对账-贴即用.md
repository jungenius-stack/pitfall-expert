# 交付对账·贴即用（零安装）

> 开工前用[入门版](入门版-贴即用.md)或完整版查坑；AI 说"做完了"那一刻，用这页纸点数。不装任何东西，把下面整段复制进**任何**聊天模型，末尾接你的原始需求。它管两件事：**防少做**（挑着干、干一半就宣告完成）、**防多做**（顺手动了没让动的东西）。

```text
你是「交付对账员」。刚有人（我或另一个 AI）说东西做完了，你逐条盘问，
拿不出证据的一律当没做：

1. 需求对账：把我的原始需求拆成一条条，逐条标 达成 / 没达成 / 没测；
   没达成的写原因，没测的给一条 5 分钟内能做的测法
2. 验证对账：凡是"跑过 / 测过 / 通过"的说法，必须粘贴那条命令和它的
   原始输出片段；贴不出来 = 没跑，标"未验证"
3. 改动对账：列出这次动过的所有文件（说不全就跑 git status /
   git diff --stat，把结果贴上来）；再答一句：有没有可能顺手动了
   清单外的东西，拿什么证实没动
4. 残留对账：还有什么没把握的假设、没测的边界、已知没修的问题，
   一条别漏；说"无"要给依据

判定：四条全有证据才许说"完成"；缺哪条明说卡在哪、下一步干什么。
禁止说"总体没问题""应该可以了"；不确定就写不确定。
需求多于 8 条先合并同类项；总输出 ≤30 行。

原始需求：
它的完成声明 / 改动说明（可选，有就贴在下面）：
```

## 两种用法

| 用法 | 怎么用 | 强度 |
|---|---|---|
| 弱用法 | 贴进项目规则文件（如 CLAUDE.md），每次交付前让干活的 AI 自己跑一遍 | 能抓"忘做/漏说"；但运动员兼裁判——它仍可能编造"原始输出" |
| **强用法（推荐）** | 干完活**开个新会话**，贴这段 + 原始需求 + 它的完成声明，让没干活的模型盘问干活的结果 | 换人批卷（CODE-043 的"非执行者验证"），一个新窗口就实现 |

## 每条对的是什么坑（出处）

- 需求对账 ← CODE-002 幻觉式完成：宣称完成但环境状态未变（MAST, Cemri et al., NeurIPS 2025, arXiv:2503.13657，"未经验证的终止"）
- 验证对账 ← CODE-004 测试通过≠正确：SWE-bench 实测 7.8%"通过"的 patch 实际错误；贴不出原始输出的"通过"一律当没跑
- 改动对账 ← CODE-043 副作用断言：验收不能只看"该来的来了"，还要看"不该多的没多"
- 残留对账 ← 三态披露契约：❓ 必须显式出现，说"无"要给依据

（这些卡在完整版 `cards/code.yaml`，触发词含「交付了 / 收工验收 / 任务完成」——完整版用户在交付类任务里本来就会命中；这页纸是把同一套知识做成交工那一刻在场、贴了就用的形态。）

## 什么时候不够用（诚实声明）

- **只管点数，不管查坑**——开工前的风险扫描用[入门版](入门版-贴即用.md)或完整版；两页纸是上下半场，不互相替代
- **靠模型自觉跑、靠你肉眼核证据**——模型若伪造"原始输出片段"，这页纸防不住；要更硬的，用完整版 CODE-002 的思路：跑状态断言脚本查环境实际状态（文件在不在、内容对不对），不信嘴
- **高频交付、要强制**——完整版 + hooks 门控，不靠任何人疲惫时的自觉
