# 交付物 4：Skill vs dsh 插件——形态选型对比与推荐

> **选型依据**：本机 dsh（DeepSeek Harness 0.2.0-rc.2）扩展机制的实地探查结果（2026-10-15，证据为 ~/.dsh/ 与 app.asar 内官方 README）+ 交付物 3 设计稿的分层需求。
> **结论先行**：推荐 **双层架构——Skill 为主体、dsh 插件为可选增强（v2）**。首版只做 Skill。

---

## 一、dsh 扩展点实测能力对比（选型的事实基础）

| 扩展点 | 形态 | 激活方式 | 强制力 | 跨外壳可移植性 |
|---|---|---|---|---|
| **Skill** | `<name>/SKILL.md` 目录（frontmatter：name/description 必填；whenToUse/user-invocable 等可选；可带 scripts/references 子目录） | 丢进扫描根即生效（热监视）；模型按 description 自行加载，或用户 `/name` 显式调用 | **纯建议性**——目录提示+模型自觉，连技能内禁令都无机制拦截 | **高**：dsh 扫描 `~/.dsh/skills` **和** `~/.agents/skills`（后者为 ZCode/Codex 等跨外壳共享目录）；SKILL.md 是事实标准格式 |
| **插件（cordis bundle）** | npm 包 + `package.json` 的 `dsh.bundle.patch` + `cordis.patch.yml` | 加入 profile bundles / 插件页安装 | **可强制**：完整 harness API（工具/命令/UI/事件/存储）；waterfall 事件（`tools/pre-execute` 等）可拦截；MCP 三层治理为硬拦截 | **零**：绑死 dsh（cordis 框架私有） |
| **Hooks 桥接** | `dsh-hooks-claude-code/codex` 插件挂载现有 hooks.json | 需显式启用 bundle | 逐点强制（退出码 2 阻塞该次调用）；运行级停止无效 | 中：复用 Claude Code hooks 生态，但 dsh 侧要装桥接插件 |

关键事实（探查实证）：
1. dsh 对 `~/.agents/skills` 原生扫描（rank 500）——**一个 skill 目录无需任何改动即可同时服务 dsh 与其他外壳**；
2. 斜杠命令两种来源：技能的 `user-invocable`（文件式，简单）与插件的 `ctx.commands.register()`（代码式，强大）；
3. 用户本机已验证的强制拦截先例：`dsh-mcp-connector` 的 ToolRuntime.guard()（三层 deny 规则硬拦截）；
4. grid-audit 技能正文里写「使用边界：禁止在做题期间调用」——**靠自觉，无机制保证**，这是所有纯 skill 的能力边界实证。

## 二、按设计稿需求逐条映射

| 设计稿需求（交付物 3） | Skill 能否 | 插件能否 | 说明 |
|---|---|---|---|
| L0–L2 定级/挖坑/过滤（知识+推理） | ✅ | ✅ | 本质是 prompt + 知识库，skill 完全承载 |
| L3 验证层（调用检索/脚本/工具实测） | ✅（携带 scripts + 宿主工具） | ✅ | skill 的 scripts/ 子目录 + 宿主 Bash/检索工具即可 |
| L4 三态披露契约（格式约束） | ⚠️ 靠指令遵循 | ✅ 可机检 | 插件可机械校验报告结构；skill 只能靠 lint 脚本半强制（产出后自查） |
| 触发①手动 `/踩坑` | ✅（user-invocable） | ✅ | 文件式即可，零代码 |
| 触发②建议性自动（检测计划信号→建议预检） | ❌ | ✅（UserPromptSubmit/agent 事件） | 桥接 hooks 或插件事件可实现 |
| 触发③强制门控（不可逆操作无报告则拦截） | ❌ | ✅（tools/pre-execute 拦截） | **能力分水岭**：只有插件能做 |
| M1 用户画像（读本地账本/会话数据） | ✅（scripts 读文件） | ✅ | 均可，权限模型不同 |
| 坑卡库版本化演进 | ✅（git 天然支持） | ✅ | markdown 文件即数据库 |
| 开源分发与社区贡献 | ✅ 门槛最低（复制目录即装） | ⚠️ 仅 dsh 用户 + npm 发布链 | skill 受众 = 所有主流外壳用户 |

## 三、决策矩阵

| 维度（权重） | 纯 Skill | 纯 dsh 插件 | **双层（推荐）** |
|---|---|---|---|
| 激活可靠性（30%） | ⚠️ 建议性，依赖 description 触发质量 | ★★★ 可强制 | ★★☆ 日常建议性 + 高危强制 |
| 跨外壳可复用（25%） | ★★★（~/.agents/skills 直通） | ☆ | ★★★（skill 层全通吃） |
| 开源受众与贡献门槛（20%） | ★★★ | ★ | ★★★ |
| 实现与维护成本（15%） | ★★★（markdown+脚本） | ★（TS/npm/cordis 测试链） | ★★（分期：先 skill 后插件） |
| 方法论完整承载（10%） | ★★☆（缺强制门控） | ★★★ | ★★★ |
| **加权总分** | **0.87** | **0.52** | **0.93** |

> 独立收敛说明：v0.2 既有稿 5.4 节「门控活在外壳/强制层，知识活在 skill 层」与本结论一致（其引述的「skill 激活率低至 ~20%」数据本调研未能核验，按未核验降级处理，不影响方向性结论）。

## 四、推荐方案：双层架构

### 4.1 首版（v1）：纯 Skill——「踩坑专家」知识引擎

```
~/.agents/skills/pitfall-expert/     ← 一个目录同时被 dsh / ZCode 等扫描
├── SKILL.md                         # L0-L5 主流程指令（精简，正文 <500 行）
│                                    #   frontmatter: name + description（触发描述）+ user-invocable
├── references/
│   ├── mechanisms.md                # M1-M12 详解（按需加载，防 SKILL.md 膨胀）
│   ├── report-template.md           # 踩坑报告模板
│   └── dod.md                       # 六条完成标准
├── pitfalls/
│   ├── domains.yaml                 # 领域注册表（含 capability 声明）
│   ├── research-decision/           # RD-001 ~ RD-008（首版 8 张坑卡）
│   ├── code-integration/            # CI-001 ~ CI-004 + falsehoods 精选
│   └── _staging/                    # math / science-ml / creative 占位（声明「未验证」）
└── scripts/
    └── dod_check.py                 # 报告 DoD 机检（六条中可机械验证的：三区存在性、
                                     #   坑卡扫描计数、证据链字段完整性）
```

**设计要点**：
- SKILL.md 只放流程主干的目的是控制注入体积（dsh 目录提示截断至 500 字符，正文按需加载）；
- 坑卡 = markdown 文件：git 版本化、社区 PR 贡献、相似召回可脚本化三合一；
- `dod_check.py` 补上 skill 形态唯一的强制力短板：报告产出后跑机检，未过 DoD 的报告模板上不允许标「合格」（自律 + 工具辅助，非拦截）。

### 4.2 二期（v2，可选增强）：dsh 插件——强制门控层

只做 skill 做不了的三件事（全部来自设计稿 3.2 触发②③与 L4 机检）：
1. **UserPromptSubmit 事件**：检测计划文件引用/支付发布意图 → 主动建议预检（把「建议性自动触发」从模型自觉变成机制保证）；
2. **tools/pre-execute 门控**：识别不可逆操作（对外发送/删除/支付类），未携带有效踩坑报告 → 拦截并提示先跑 `/踩坑`；
3. **报告机检自动化**：L4 披露契约的结构校验从「自觉跑脚本」变为「自动跑」。

插件定位为**可选增强包**，不承载任何方法论知识——知识只有 skill 一个源头，杜绝双份维护漂移。

### 4.3 开源仓库结构草案（GitHub）

```
pitfall-expert/                      # 仓库名候选：pitfall-expert / pitfall-scout / caikeng-expert
├── README.md（EN）+ README.zh.md    # 一图看懂 + 30 秒安装
├── LICENSE                          # 代码 MIT + 文档/坑卡 CC BY 4.0（双许可，见下）
├── skill/                           # §4.1 的完整内容（安装 = 复制此目录）
├── plugin-dsh/                      # v2 占位（roadmap，首版空目录 + 设计说明）
├── cases/                           # 坑点案例库（10 条回放考题公开——可复现的验收集）
│   └── 坑点案例库-v1.md
├── docs/                            # 四份交付物 + reference
└── CONTRIBUTING.md                  # 坑卡贡献协议：三件套（capability 边界 + ≥5 张带溯源坑卡 + ≥1 条案例回放）
```

**许可证建议**：代码（scripts、未来插件）**MIT**；文档与坑卡内容 **CC BY 4.0**——坑卡的价值在于被引用和传播（救命清单），BY 条款保留署名即可。若希望简化为单一许可，全 MIT 亦可接受（备选）。

**仓库名建议**：`pitfall-expert`（直译、好搜）；备选 `pitfall-scout`（「任务前侦察」语义更准）。中文名「踩坑专家」在 README 首行绑定搜索。

## 五、明确不做的事（本期边界）

1. **不实现**——本交付物止于选型推荐，按任务书要求经用户确认后再进入实现；
2. **不做 Claude Code / ZCode 的插件适配**——skill 形态天然兼容（~/.agents/skills 共享扫描），无需单独适配；如未来做强制门控的 Claude Code 版（hooks.json），走 hooks 桥接复用，不在首版范围；
3. **不发布 math/science-ml/creative 领域的任何承诺**——仅注册占位（设计稿 4.1 领域扩展协议）；
4. **不追求坑卡数量指标**——宁缺毋滥、版本化演进（综述 5.8），首版 12 张左右全部带溯源。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| Skill 建议性导致「该触发时没触发」 | description 写足触发场景；用户习惯 `/踩坑` 显式调用；v2 插件补事件触发 |
| SKILL.md 过长导致加载率下降 | 主干 <500 行，机制详解放 references 按需加载 |
| 坑卡质量参差（社区贡献后） | CONTRIBUTING 三件套协议 + verified 字段分级（case-replay > literature > unverified） |
| dsh 版本升级破坏插件 API | 首版不依赖插件；v2 插件锁定 engines.dsh 语义版本 |
| 「踩坑专家」自身谄媚（顺着方案找补） | 设计稿第六节已列防线（隔离生成/独立上下文），实现时写入 SKILL.md 硬约束 |
