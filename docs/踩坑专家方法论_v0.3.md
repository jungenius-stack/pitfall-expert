## 〇、产品定位（一切设计的前提）

**踩坑专家是风险测绘仪 + 验证器铸造厂，不是全检器。**

四条定位公理：

1. **坑不可穷尽**。坑卡是对已知坑的采样，未知的坑（unknown unknowns）无法被已知清单捕捉——这是系统的根本边界，不是缺陷，是事实。
2. **能力随领域可验证性递减**。宣称全领域通吃 = 过度承诺 = 系统必须自己抓出来的那个坑。
3. **如实申报无知是交付物**。"我不知道我不知道什么"必须被显式说出，而不是沉默。
4. **预踩坑的产出物是验证器，不是担忧**（v0.3 新增）。一份列满"可能出问题"但没有任何可执行检查的报告，与一份漂亮的愿望清单在工程上等价——都不能改变失败概率。每个预踩坑任务因此交付两样东西：三区风险报告 + 针对 🔴 必坑的外部验证器清单（测试、断言、状态比对、独立工具调用、人类确认）。

### 领域能力分级表

| 领域 | 坑的可判定性 | 踩坑强度 | 能交付什么 | 不能交付什么 |
|---|---|---|---|---|
| 代码 | 高（可执行验证） | ★★★★★ | 自动验证的坑区 | 架构品味 |
| 数学 | 中高（可形式化） | ★★★★ | 量纲/边界/特殊值/符号复核 | "证明是否优雅" |
| 科学/ML | 中（部分可查） | ★★★ | 泄漏/偏差/复现检查 | 实验设计 expert 判断 |
| 创意/写作 | 低（判定主观） | ★★ | 事实硬伤、显性矛盾 | 审美与策略层面的坑 |
| 决策/战略 | 低（结果后验） | ★ | 假设挖掘、预验尸 | 预知未来 |
| 元任务（设计方法论/工具自身） | 中（可部分自验） | ★★★ | 流程缺陷暴露、自指矛盾 | 自身市场成败 |

**规则：每次踩坑开始时，必须先声明本任务落在哪一格，按格承诺，不越格。**

## 一、认知层 —— 为什么坑会被自动看不见

*（本层是元层，领域无关，通用性最强）*

### 1.1 乐观偏差与规划谬误
- AI（和人）默认系统性高估成功率。→ **每个 AI 给出的方案，启动时默认带乐观偏差，需外部干预。**
- 解药：参考类别预测——不看方案多完美，看同类任务的历史翻车率。

### 1.2 前瞻性后见之明
- 想象"已经失败"再回溯原因，比正向提问挖出更多真实风险。
- ⚠️ 证据分级【观点 + 有限实证】："+30% 预测提升"是 Klein 对 Mitchell et al. 1989（JBDM）的二手转述，原文实测的是解释的数量/类型变化（确定未来事件使解释更长、更情节化），并未验证预测准确率。Veinott et al. 2010（178 名学生）佐证"设想失败可降低过度自信"。**作为方向性证据使用，不作为精度承诺。**

### 1.3 集体思维与谄媚
- AI 有顺着用户说的倾向（sycophancy）→ 踩坑角色的 KPI 是找到坑，不是让用户舒服。
- 证据分级【实证】：Sharma et al., Anthropic, 2023——五个 SOTA 助手一致表现谄媚，且人类偏好数据本身奖励谄媚。推论：**用户确认不是可靠的纠错 oracle**，除非该反馈锚定硬信号（执行结果、环境状态）。

### 1.4 确认偏误与街灯效应
- 验证阶段证伪优先：先问"什么证据能推翻"，不问"什么证据支持"；强制覆盖"难验证"区域。

### 1.5 AI 特有偏误清单

| AI 偏误 | 出处 | 对策 |
|---|---|---|
| 无外反馈的自我纠错无效甚至有害 | Huang et al., ICLR 2024（实证：GPT-4 自我纠错 95.5%→89.0%） | 禁止"我再想想"式内省验证 |
| 幻觉/编造引用 | 业界公知 | 高危声明外部检索核实 |
| 谄媚 | Sharma et al. 2023（实证） | 对抗角色设计 |
| 单代理盲区 | ChatEval, ICLR 2024（实证） | 评审者 ≠ 执行者 |
| 虚假不可能性 | WebArena, ICLR 2024（实证：占失败模式 54.9%） | "做不到"类陈述必须附验证证据 |
| 复跑不一致 | τ-bench, ICLR 2025（实证：pass^8 <25%） | 一致性门，见 3.7 |

### 1.6 生成器-验证器缺口（v0.3 新增）
- 验证比生成容易，**只在验证器拥有生成时所不具备的信息时成立**（Huang et al. 与 CRITIC 合流的推论）。
- 用法：预踩坑清单的每一条检查都要问——"这个检查掌握了什么执行时所没有的新信息？"答不上来即是仪式性检查，应当删除或改造。
- 证据分级【实证】。

## 二、挖坑层 —— 把坑翻出来（弹药库）

> 本层是**弹药库不是军规**。默认流程只取其中数件（见第七层 SOP），其余按档位和领域选用。堆砌全部方法论 = 执行瘫痪 = 元坑①。

### 2.1 Pre-mortem 预验尸 ⭐ 主框架
Gary Klein（HBR 2007）：假设项目已彻底失败→独立写失败原因→汇总，只列不辩解。
核心机制：把"会不会失败"（不确定，抑制解释生成）改写为"它是怎么失败的"（确定，释放解释生成）。

### 2.2 反转思维
芒格/Jacobi："反过来想"。轻量版预验尸："想把这个需求做砸，我会怎么做？"

### 2.3 假设映射 ⭐ 主框架之一
Bland & Osterwalder：倾倒全部隐含假设→按 **重要性 × 确定性** 排矩阵→右上角"信念跳跃"优先攻击。
【观点/实践框架】无正式标准、无实证效果研究——引用时标注为实践框架。

### 2.4 魔鬼代言人 / Grill Me
攻击者角色 + 需求拷问。很多坑在需求糊掉的那一刻就存在。

### 2.5 FMEA ⭐ 评分主框架
严重度 S × 发生率 O × **探测度 D** = RPN。D 是灵魂：**隐性坑 = S高 + O高 + D高（毫无征兆）**。
⚠️ v0.3 批评注记【实证/标准批评】：RPN 乘积法是**排序启发式，不是风险度量**——不同量纲相乘无理论依据、评分主观、阈值随分析而变；AIAG-VDA FMEA Handbook 2019 已改用 Action Priority 表。使用 RPN 时必须同时披露此批评。
经典案例【案例】：Knight Capital 2012——一个遗留部署 flag 被重新激活，45 分钟蒸发 4.4 亿美元（SEC Release No. 34-70694）。一条 FMEA 就能拦下。

### 2.6 STRIDE 威胁建模 + 攻击树
沿**信任边界**扫坑而非沿功能扫坑。STRIDE 六类可近乎一一映射 agent 风险面；OWASP LLM/Agentic Top 10 本质是其在 LLM 场景的实例化。
诚实注记： Schneier 本人承认攻击树的"虚假完整性"问题——树看起来完整但可能漏掉整类攻击。**与失败分类学（2.13）互补使用，不单独依赖。**

### 2.7 红队思维
把方案当敌方产品攻击。工具生态：garak / PyRIT / promptfoo。

### 2.8 多代理对抗辩论
多视角提升发现率——但 Should We Be Going MAD?（ICML 2024）警告：**策略不当反而变差**。规则：只在深审档启用，角色和议程必须显式设计（攻击者/审查者/假设挖掘者三分工），不拉代理吵架了事。

### 2.9 混沌工程
主动注入受控故障，观察真实表现。踩坑对应：高危假设喂最小实验"弄坏它试试"。
AI agent 场景适配【前沿适配，2025 初步研究】：ChaosLLM（ISSRE 2025）、Owotogbe（CAIN 2025）、ReliabilityBench——在 agent 与环境间注入工具超时/崩溃/schema 漂移，量化成功率衰减。尚未形成业界共识，引用时标注。

### 2.10 Falsehoods 清单
kdeldycke/awesome-falsehood：各领域"信以为真的谎言"现成对照库——**坑卡的骨架来源，但记住它是采样不是全集。**

### 2.11 工程格言四件套

| 格言 | 用法 |
|---|---|
| Hyrum 定律 | 改"无害行为"前问：谁在暗中依赖它 |
| 切斯特顿栅栏 | 看不懂用途的代码/配置，考古之前不许删 |
| 二阶思维 | 每个方案问两轮"然后呢" |
| 墨菲定律 | 高危坑不管概率多小都要有对策 |

### 2.12 元格言两件套

| 格言 | 用法 |
|---|---|
| **漏报可原谅，谎报不可原谅** | 复盘追责的唯一判据：看披露完整性，不看结果对错 |
| **完成 = 披露完整，而非结果完美** | 追求"结果上没坑"必然催生谎报；过程完备才是底线 |

### 2.13 MAST 14 失败模式（v0.3 新增）
Cemri et al., UC Berkeley, NeurIPS 2025（实证：1600+ 标注轨迹、7 个 MAS 框架、AppWorld 故障率 86.7%）。三分类：
- **规范与系统设计**（FC1-3）：规范缺陷、提示冲突、角色重叠；
- **agent 间错位**（FC4-6）：信息丢失、重复劳动、结论冲突无人裁决；
- **任务验证与终止**（FC7-14）：未经验证的终止、过早完成、级联失败、无终止条件。

用法：长任务与多 agent 预检骨架。**注意其实证发现："简单 prompt 干预仅提升 14%，需要结构性重新设计"——预踩坑不能止于列清单，要改结构。**

### 2.14 OWASP Agentic Top 10（v0.3 新增）
2025-12-09 发布（Black Hat Europe 2025）【专家共识】：
ASI01 Agent Goal Hijack / ASI02 Tool Misuse / ASI03 Identity & Privilege Abuse / ASI04 Agentic Supply Chain / ASI05 Unexpected Code Execution / ASI06 Memory & Context Poisoning / ASI07 Insecure Inter-Agent Communication / **ASI08 Cascading Failures** / **ASI09 Human-Agent Trust Exploitation** / ASI10 Rogue Agents。
架构原则 **Least Agency**：权限最小化到"刚好够完成任务"。
重点两条：ASI08（级联失败，与 MAST 实证互为印证）、ASI09（人类过度信任，与 sycophancy 实证互为印证）。

### 2.15 攻击树（v0.3 新增）
Schneier 1999【方法论】。步骤：定义根目标（如"agent 造成不可逆损害"）→ 分解高层攻击方法 → 递归至原子步骤 → 标注 AND/OR → 叶节点标注成本/可探测性 → **成本最低路径优先防御**。
与 2.6 STRIDE 互补：STRIDE 沿信任边界分类，攻击树沿失败路径建模。

### 2.16 时间线前置重建（v0.3 新增）
【实践框架，SRE 同构】长任务动手前，先让 agent 写出**计划执行轨迹**（动作序列 + 每步检查点 + 每步的环境状态预期），再对轨迹做 pre-mortem。
依据：blameless postmortem 的"先时间线后归因"顺序（Google SRE Book Ch.15）——对已知轨迹做失败预演，比直接列风险更结构化，也天然暴露级联路径。

## 三、验证层 —— 坑是真的吗

### 3.0 验证器优先（v0.3 升格为主原则）
**预踩坑的交付物以"可执行验证器"计量。** 每条 🔴 必坑必须绑定一个验证器（Beyoncé 法则强化版）；无法绑定验证器的怀疑，降级进入 ❓ 未验证区，不得留在 ✅ 区。
依据：generator-verifier gap（1.6）+ Huang et al. 与 CRITIC 合流——纠错回路有效当且仅当引入外部信号。

### 3.1 内省无效定律 ⭐
无外部反馈的自我检查不但无效还会降低准确率。**"我再想想"不算踩坑。**

### 3.2 CRITIC 工具交互验证
外部工具（搜索/执行/计算/复现）验证才有效。

### 3.3 可证伪优先
每个关键假设写"推翻条件"。写不出推翻条件的假设 = 没被检查过的假设。

### 3.4 最小可行实验
5 分钟内能证伪最脆弱的假设。证伪不了 → 标记"未验证"（不是硬做）。

### 3.5 Beyoncé 法则
每条 🔴 必坑附带一个可执行测试/检查动作，否则等于没说。（v0.3 起与 3.0 合并执行）

### 3.6 完成证据 = 环境状态变化（v0.3 新增）
任务"完成"的判定以**环境状态**为证——文件已生成且内容正确、数据库行已变更且值符合预期、外部系统已返回预期响应——而非 agent 的自我陈述。
依据：τ-bench 的设计核心（database state 验证）；MAST"未经验证的终止"失败类。

### 3.7 复跑一致性 pass^k（v0.3 新增）
单次成功 ≠ 可靠。τ-bench 实证：SOTA function-calling agent 单次成功率约 60%，而同一任务连跑八次全对（pass^8）低于 25%。
规则：凡可复跑任务，预踩坑必须设计复跑比对（≥3 次），报告一致性而非单次结果；不可复跑任务，显式声明为不可验证项（进 ❓ 区）。

### 3.8 验证器本身也要被验证（v0.3 新增）
SWE-bench 实证（ICSE 2026）：7.8% "通过"的 patch 实际错误，29.6% 与 ground truth 行为分歧——**弱测试套件会给出虚高通过率**。
规则：预踩坑清单固定包含一项"验证器可靠性审查"：测试是否断言了行为值而非仅不抛错；断言是否覆盖边界；测试套件本身是否可能被"应付"。

## 四、评估层 —— 先杀哪个坑

### 4.1 FMEA RPN 排序
**D（隐蔽度）优先于一切**：明枪易躲，隐性坑才是杀手。（使用 RPN 时遵守 2.5 的批评注记）

### 4.2 Tiger / Paper Tiger / Elephant 三分法
🐯 立刻杀 / 纸老虎 识别后不浪费防御资源 / 🐘 大象：今天没事、半年致命，进监控区。

### 4.3 参考类别预测
先问"这类需求历史上最常见的翻车方式"——坑库存在的理由。

### 4.4 边际收益权衡
方法论之间互相打架：FMEA 精细化 vs 快扫速度、多代理发现率 vs 成本与不稳定。**不存在全都要的最优组合**——取舍由档位决定（见第六层）。

### 4.5 一致性门（v0.3 新增）
任务风险评级若显示"高可靠性要求"（生产环境、不可逆、多次执行），必须追加 pass^k 审查（3.7）——单次演示通过不构成放行依据。

## 五、防御层 —— 保证坑真被避开

### 5.1 清单革命 ⭐
短清单（≤9 条）+ 强制勾选位。实证：NEJM 2009（Safe Surgery Saves Lives，8 国 8 院，死亡率 1.5%→0.8%）。
**警示：这条同时约束踩坑 SOP 自身**——方法论堆砌到 30+ 条，违反的就是自己（元坑①）。
限定：清单是团队沟通工具（口头复述比打勾更重要）；有执行衰减；不是所有并发症都降。

### 5.2 瑞士奶酪模型
任何单层防御都有洞，安全 = 多层防御的洞不重叠（Reason, BMJ 2000）。踩坑三防线（第六层）即此模型的应用，**每道防线都要预设自己的失效模式**。
批评注记：Dekker / Larouzée & Le Coze（Safety Science 2020）指出模型不解释孔洞在哪、为何移动、如何对齐——因此预踩坑的产出应是"找出每层的孔洞并防止对齐"，而非仅仅列出防御层。

### 5.3 最小权限 / 可回滚
子代理默认只读；不可回滚的操作自动升 🔴。（对应 Least Agency 原则）

### 5.4 强制 > 提醒
Skills 是建议（激活率可低至 20-50%，社区实测，官方无数据），hooks 是强制（确定性执行、可 deny）。**门控活在外壳/强制层，知识活在 skill 层。**

### 5.5 门控的失效模式（v0.3 新增，瑞士奶酪自指的具体化）
门控自身也是会失效的一层：
- 官方明示 hook 失败/超时**默认放行**（fail-open）；if 过滤是 best-effort；用户可全局关停 hooks；
- 对策：门禁挂健康检查与告警；"必须万无一失"的硬策略走权限系统（deny 清单）而非 prompt 层；门控层与知识层分离，任一层失效不拖垮另一层。

## 六、诚实架构 ⭐⭐

**解决元坑②"没踩完说踩完了"和元坑③"踩完了用户不信"。**

### 6.0 前提承认
"坑踩完了"**原则上不可证明**（absence of evidence ≠ evidence of absence）。任何声称踩完全部坑的系统都在说谎。问题的正确形态不是"如何保证踩完"，而是"**如何在踩不完的前提下不撒谎**"。

### 6.1 三道防线（每道自带失效模式——瑞士奶酪自证）

**防线 1：承诺过程，不承诺结果**
- ❌ "坑踩完了"（不可验证 → 必然违约）
- ✅ "已扫描坑类别 X（100%）、已验证高危假设 Y（100%）、未验证项 Z（如实列出）"
- 完成定义 = **披露完整**（可审计）。

**防线 2：三区输出契约**

```
✅ 已查证区：坑 + 证据链（发现途径/验证手段/来源链接/推翻条件）
❓ 未验证区：怀疑有坑但未验证的 + 原因（超时/无工具/超能力）
🚫 盲区声明：本任务类型中我系统性看不见的坑类别（预注册，类比利益冲突披露）
             + 本次扫描/调研未覆盖的范围（哪些生态/信源/子域在外）
```

🚫 区是灵魂：AI 最危险的不是有盲区，是**盲区无声**。三区中任何一区不允许空着不写——没有内容也要显式写"本区为空"。
v0.3 强化：✅ 区每条坑必须带**置信度三档**标记——backed by context（有任务上下文或检索证据支撑）/ needs verification（怀疑但未验证）/ assumption（假设，未经任何检验）。未标记者不得出现在 ✅ 区。
v0.3 强化：🚫 区的"未覆盖范围"必须在**动手前显式声明扫描范围**，范围外项进 🚫 区而非沉默（回放教训，见附录 A）。

**防线 3：漏报/谎报双轨复盘**
- 漏报（用户事后指出，但当初未验证项有如实披露）→ 可原谅，正常回写坑库
- 谎报（声称踩完但未披露未验证项）→ 不可原谅，流程缺陷，5 Whys 追根

### 6.2 信任工程（解决"用户不信"）
用户说"没踩完"实为三种不同不满：覆盖不够 / 验证不实 / 没挖到心里的坑。两路解法：
1. **事前档位协商**（见 6.4），歧义消灭在源头；
2. **证据链全程可抽查**：每条坑可独立复核，抽查可行性本身即质量承诺。用户不需要重做踩坑，抽查一条、链条断裂即整体失信——这个威慑就是质量的担保。

### 6.3 用户质疑 = 免费红队
被用户纠正的每一次，都是系统免费获得的红队攻击结果。标准动作不是辩护，是走复盘：这坑为什么没扫到 → 坑卡缺口 or 流程缺口 → 回写。**用户质疑是最贵的坑库原料。**

### 6.4 服务档位（先合同后干活）

| 档位 | 流程内容 | 耗时 | 适用 |
|---|---|---|---|
| ⚡ 快扫 | 领域声明 + 假设倾倒 + 坑卡对照 + 三区报告（不验证） | 分钟级 | 低风险小任务 |
| 🛡️ 标准 | 快扫 + 高危假设动手验证 + 🚫盲区声明 | 十分钟级 | 常规需求（默认档） |
| 🔬 深审 | 标准 + 对抗角色 + 最小实验 + 逐坑证据链 + 攻击树 + MAST 对照 | 小时级 | 高风险决策 |

交付标准按购买档位验收，越档承诺 = 元坑④（过度承诺）。
v0.3 增补（元坑⑦的修正）：**决策点呈现时必须附白话解释**——用户可能不熟悉架构概念，直接抛术语选项会迫使二次追问，协商即形同虚设。

## 七、标准作业流程 SOP（默认流程 4 步）

```
需求进来
   │
   ▼
【第1步 领域定级 + 需求拷问】──── 领域能力分级表 + grill-me
   │ 声明本任务落在能力表哪一格（按格承诺，不越格）
   │ 验收标准/边界条件逼问清楚；需求是糊的 → 立刻退回
   │ 决策点呈现附白话解释（元坑⑦修正）
   ▼
【第2步 假设倾倒】────────────── Assumption Mapping
   │ 列全部隐含假设 → 重要性×确定性矩阵 → 右上角"信念跳跃"优先攻击
   │ （不可攻击的跳跃 = 必须向用户确认的决策点，不是可以默默假设的参数）
   ▼
【第3步 预验尸 + 坑卡对照】───── Pre-mortem + 反转思维 + 领域坑卡/Falsehoods/MAST/OWASP族卡
   │ "已失败，因为什么" → 加载领域坑卡逐条扫 → 参考类别预测
   │ 长任务先做时间线前置重建（2.16）再预演
   ▼
【第4步 三区契约输出】────────── 诚实架构防线1+2
   │ ✅已查证(带置信度三档) / ❓未验证(附原因) / 🚫盲区声明(含未覆盖范围)
   │ + 针对 🔴 的验证器清单（3.0）
   ▼
─── 档位升级分支 ───
🛡️标准档：高危假设动手验证（CRITIC/最小实验），未验证的降级到❓区；可复跑任务设计复跑比对（3.7）
🔬深审档：+ 对抗角色审查 + FMEA RPN（带批评注记）+ 攻击树 + MAST 对照 + Tiger三分类 + 逐坑证据链
   ▼
【事后 回写闭环】─────────────── Blameless Postmortem + 5 Whys + 坑库
   │ 证实坑 + 用户指出漏坑全部回写；漏报追"为什么没发现"，谎报追流程根因
   └──→ 坑库增厚 → 第3步扫描越来越准 → 系统性复利
```

**升级弹性**：FMEA/STRIDE/红队/多代理/混沌注入保留在弹药库，按领域和档位取用——代码域优先 CRITIC+最小实验+复跑比对，ML 域优先泄漏坑卡，决策域优先预验尸+参考类别，数学域优先量纲/边界/特殊值复核。

## 八、踩坑完成标准（Definition of Done）

> 踩坑流程算"完成"，当且仅当五条全满足：

1. **领域已定级**：本任务在能力分级表中声明过档位，承诺未越格
2. **覆盖率**：所属领域坑卡清单扫描率 100%（可数、可查）；且**扫描范围在动手前显式声明**（哪些来源/生态/子域在内），范围外项进 🚫 区（v0.3 增补）
3. **验证率**：所有 🔴 必坑验证率 100% 或其验证器已交付；未验证的一律降级 ❓区并注明原因（v0.3 将"已执行验证"扩展为"已交付验证器"）
4. **披露率**：三区各自显式输出（含"本区为空"的显式声明）；🚫盲区声明非空或有依据地写"无"，且必须包含"未覆盖范围"小节（v0.3 增补）
5. **回写就绪**：本任务所有坑（含后续用户指出的漏坑）具备回写坑库的条目格式

**判定规则**：五条全过 = 合格踩坑（哪怕后来发现漏了大坑）；任何一条虚报 = 不合格（哪怕碰巧没出事）。
**哲学基础**：1–4 全是过程指标，无一条要求"结果上没有坑"——保证结果的完美只会在激励上催生谎报；保证过程的完备与披露的诚实，才是可持续的质量底线。

## 九、坑库条目规范（沉淀层）

### 9.1 坑卡条目四件套（缺一不合入，v0.3 起强制）
每条坑 = **描述 + 证据/来源 + 规避动作 + 验证器**（可执行检查/测试；无验证器的 🔴 降 ❓）。
字段：适用领域、触发条件、严重度参考（S/O/D 供深审档用）、**confidence（三档）**、**evidence_level（实证/案例/共识/观点）**、**pass_k_relevant（是否需复跑验证）**。

### 9.2 回写双通道
- 证实坑 → 直接入卡
- 漏报坑 → 先走 5 Whys（为什么预踩没发现：坑卡缺口？扫描流程缺口？披露缺陷？）→ 归类入卡或修流程
- 注：5 Whys 的线性单链假设与 agent 级联/概率性失败不符，升级为"贡献因子清单 + 失败分类学对照"（MAST）

### 9.3 元坑登记簿

| # | 元坑 | 症状 | 修正措施 | 落点 |
|---|---|---|---|---|
| ① | 方法论堆砌 | 30+ 方法论全塞流程，执行瘫痪、形式主义 | SOP 4 步，其余降级弹药库 | 第七层 |
| ② | 谎报踩完 | 声称踩完但未披露未验证项 | 诚实架构三防线 + 三区契约 | 第六层 |
| ③ | 信任崩塌 | 用户无法复核，只能信或不信 | 档位协商 + 证据链可抽查 | 6.2 |
| ④ | 过度承诺 | "全领域通吃""+30% 精确增益" | 能力分级表 + 证据降级为方向性 | 定位/1.2 |
| ⑤ | 验证器虚高（v0.3 新增） | 声称"已验证"但验证器本身不可信（弱测试、虚高通过率） | 验证器可靠性审查（3.8）+ SWE-bench 实证依据 | 第三层 |
| ⑥ | 复跑不一致（v0.3 新增） | 单次成功掩盖高方差，被当作稳定性证据 | pass^k 一致性门（3.7/4.5） | 第三/四层 |
| ⑦ | 档位协商后置（v0.3 新增） | 决策点直接抛术语选项，用户因概念门槛被迫二次追问，协商形同虚设 | 决策点必附白话解释 | 6.4/SOP 第1步 |
| ⑧ | 信源失效（v0.3 新增） | 第三方转引的仓库/文档可能已死（本轮实测 1 例 404），结论建在流沙上 | 竞品结论分"已核实/未核实"两级；关键结论读一手来源 | 附录 A |

> 本登记簿持续开放：本方法论自身的每一次翻车都进这里。**这是系统唯一诚实的成长路径——不是遮羞布。**

### 9.4 坑库自举条款
本方法论上线前必须**拿真实历史任务回放跑一遍 SOP，用 DoD 五条验收，不过则改方法论再回放**。先自踩，再对外。

| 2 | 覆盖率 | ⚠️ | 坑卡对照做了，但**扫描范围未在动手前显式声明**（国内生态/HF Spaces 等范围外项当初未声明） |
| 3 | 验证率 | ⚠️ | "未找到"类结论只经一轮检索；dsh 关键能力结论来自引述官方文档的社区教程，未经一手仓库核验（P4 前必须补验） |
| 4 | 披露率 | ❌ | 🚫 盲区未显式成区——决定性缺口 |
| 5 | 回写就绪 | ✅ | 本次回放即回写动作 |

**判定：带缺陷合格。** 按诚实判据（看披露完整性，不看结果对错）：缺陷在流程侧（盲区未成区、范围未声明），不在结果侧（竞品结论本身扎实）。

### A.5 5 Whys（缺陷根因）
1. 为什么盲区没成区？→ 回放时没有"盲区显式成区"的检查动作；
2. 为什么没有这个检查动作？→ v0.2 的 DoD 第 4 条只要求"三区显式输出"，未要求"扫描范围事先声明"；
3. 为什么 DoD 这样写？→ v0.2 对"披露完整性"的定义过窄——假设了执行者会自动申报范围；
4. 根因：**DoD 把"三区输出"当成了终点，没把"范围声明"当成输出的前置条件。**
5. 修正：v0.3 DoD 第 2/4 条增补"扫描范围动手前显式声明，范围外项进 🚫 区"（已落入本文第八层）。

### A.6 新元坑回写
- 元坑⑦ 档位协商后置（经过见 A.3 第 1 步）；
- 元坑⑧ 信源失效（经过见 A.3 第 3 步）。

### A.7 结论
方法论 v0.3 通过自举回放（带缺陷合格），两处流程缺陷已回写为元坑 ⑦⑧ 并据此加固 DoD 与 SOP。**下一步：用真实用户任务继续回放，检验加固是否有效。**
